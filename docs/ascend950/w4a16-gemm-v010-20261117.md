# W4A16 GEMM — Ascend 950 schedule and acceptance (2026-11-18)

## Result and qualification

All **15 manifest cases** pass full-output verification, the original numerical
tolerances, negative controls and input preservation. Against the same-process vendor
contract the PR block was raised on — `torch_npu.npu_weight_quant_batchmatmul` with the
identical packed weight, scales, zero points and group size — **all 15 ratios are at
least 0.8**; the minimum is **0.920** (`decode-long-k-float16`).

`ratio = vendor / TileOPs`; only a ratio above 1 means faster than that reference. These
are development-machine results, **not a replacement for canonical PR CI**.

## Schedule

- One fused kernel per call. A pool of AIV producers unpacks the Marlin-packed INT4
  weight straight into compact-NZ L1 tiles while the Cube contracts the previous tile;
  a fixed grid of 32 blocks covers the persistent M/N tiles.
- **Group-paired nibbles.** Each packed byte carries quantization group `2p` at k=b in
  its low nibble and group `2p+1` in its high nibble, so `vintlv(low, high)` places one
  group on the even lanes of the vector and the other on the odd lanes. A single
  signed `int8 -> fp16` conversion then takes a whole group: the per-group `vunpack`
  and the activation permutation pass are both gone, because the emitted order is the
  natural k order inside each group.
- **Zero point in FP16.** Both nibble values and the zero point convert to FP16 before
  the subtraction, so the full `uint8` zero-point range `[0, 255]` stays exact; the
  scale multiply and the NZ store follow.
- Contractions whose whole K tile fits on chip keep the resident-activation schedule.
  The paired layout applies when `K >= 512` and a whole 256-value K tile fits; shorter
  or unpaired reductions keep the previous packing and permutation, and the column
  atom is narrowed only over candidates that divide `N` and stay 16-aligned.
- The weight format is owned by this backend's `repack` (`AscendW4A16RepackKernel`) and
  handed to the timed call by the workload binder, as `GEMMW4A8FwdOp` already does. The
  shared `repack_w4a16_weight`/`unrepack_w4a16_weight` helpers keep their Marlin
  semantics for the CUDA backend and the CPU contracts.

## Measurement and evidence

- Physical device: `Ascend950DT_9582`, **32 Cube / 64 Vector**, normal platform clocks.
- Timer: the shared nightly raw-profiler timer — **3 warmups + 15 independent profiler
  windows**, 1 GiB eviction, no event/wall-clock fallback or sample trimming.
- Correctness: each case checks the final measured output outside timing; candidate and
  vendor run in the same process, same inputs, in the same lease.
- Device discipline: every batch runs under the host NPU reservation
  (`npu_guard_transport` lease), acquired on a clean idle device and released after a
  final idle probe.
- Raw profiles, per-case plans, correctness receipts and the driver log are retained at
  `/root/wt/pr83-perf-20261117/evidence/perf_v21/` on the development host.

## Rejected attempts

- Folding the zero-point subtraction out of the unpack (`D = A@(q*s) + asum@(-z*s)`), in
  three implementations: the prepass and the trailing GEMM always cost more than the
  three saved vector ops (tp8 13.6 -> 36.8 us, llama 33.8 -> 86.8 us).
- Deeper K pipelines (`stages=3`, `tile_n=128`, single-versioned weight buffer): all
  slower, between 2% and 45%, because each variant either breaks the producer-to-L1
  overlap or shrinks the column atom.
- Explicitly unrolling the producer row loop: code growth swamped the address savings
  (long-k 302.9 -> 3907 us).
- Scalar-operand `vadds`/`vmuls` for the zero point and scale: UB scalar-load latency
  dominated (tp8 13.6 -> 28.2 us).
