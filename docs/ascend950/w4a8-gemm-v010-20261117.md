# Ascend 950 W4A8 GEMM (v0.1.0)

## Scope and contract

`GEMMW4A8FwdOp` on Ascend 950 (950DT, 32 Cube / 64 Vector): an FP8 activation
against a signed INT4 weight whose values carry a 128-element group scale,
contracted in FP8, then scaled per token and per output channel and written as
bfloat16. **98 manifest cases** cover DeepSeek-R1 and Llama-3 70B up/down
projections from batch-1 decode to 4096-row prefill, plus their eight-way
tensor-parallel shards.

The weight is packed two INT4 values per byte, low nibble first, each a signed
two's-complement value in `[-8, 7]`. The reference rounds `q * group_scale` to
`float8_e4m3fn` before contracting, so the kernel materializes exactly that FP8
operand: the value the tensor core multiplies is the value the reference
produces, and the tolerance carries no unpack error.

The implementation (`AscendGEMMW4A8Kernel`,
`src/tileops/_kernels/ascend/gemm/w4a8.py`) was ported unchanged onto
`ascend950-v0.1.0` in PR #82. The public arguments, the packed-weight ABI and the
numerical tolerance are unchanged from the `ascend950` contribution.

## Schedule

Three passes, one kernel each, run back to back on the vector and Cube cores of
the same device:

- **Unpack.** `wb[n, k] = fp8(q * group_scale[n, k // 128])`, on the vector
  unit. `UNPK4_B8` puts one packed byte in the low byte of each 32-bit lane, so
  one vector step covers a whole 128-value group: the low nibbles are the even K
  values, the high nibbles the odd ones, `vintlv` re-pairs them into K order and
  `PK4_B32` stores the FP8 lanes back to back. Two rows per block keep the
  packed read and the FP8 write in flight. The pass is bandwidth-bound — it
  reads `N*K/2` bytes and writes `N*K` — and runs at 1.6–1.7 TB/s.
- **GEMM.** A native FP8 NT matmul: a 256-deep K stage with two operand versions
  at every row count, a 16/64/128/256-row tile that grows with the call and does
  not compute rows it has no tokens for, and a 224-wide column tile wherever N
  allows it. The row tile shrinks by 64 rows when the L1 operand budget cannot
  hold the deeper stage at 256 rows. FP32 accumulation in L0C, one 64-deep MAD
  step per L0 operand version.
- **Scale.** `out = bf16(acc * token[m] * channel[n])`, on the vector unit, one
  row per block in column tiles (a wide N is walked in the widest divisor of N
  that keeps the row buffers inside the vector unit's 192 KiB). The pass is
  memory-bound on the FP32 accumulator it reads back.

The unpack has no DeepGEMM counterpart: DeepGEMM's Ascend kernels take MX E8M0
block scales, whose float32 slots must hold exponent-only factors, so a
per-group FP8 scale grid is not hardware-native there. The GEMM is DeepGEMM's
`fp8_gemm_nt` translated to TileLang — same persistent tile scheduler and L0
staging, with the tiles re-tuned here.

## Baseline status

The published comparison snapshot (`yyttt6/TileOPs.github.io@63c58f47`, frozen
2026-11-16) carries **98 rows for this op, all `torch-eager`
(`ascend950-isolated-ffts-v3`)**. No vendor library row exists: `torch_npu` /
ACLNN expose no W4A8 entry (`npu_weight_quant_batchmatmul` serves A16W4/A16W8),
and DeepGEMM-Ascend's kernel is an FP8 GEMM of a different function.

The 98 published `torch-eager` records are valid reference baselines for their
recorded complete workload. Every case passes the 0.8 threshold **against this
published reference set**. The reference ratios below (`torch-eager / TileOPs`,
10.25–28.40×) must not be advertised as vendor speedups or a global fastest-library
claim. Vendor comparison currently has no admitted same-contract measurement;
absence from the snapshot alone does not prove that no vendor implementation or
complete composition can exist. Applicability and any additional vendor coverage
remain tracked in #59 / #46; the operator itself is not labelled not applicable.

## Known limits

- The unpack writes FP8 to GM and the GEMM reads it back, so decode rows pay a
  full weight round trip per call; the pass does not shrink with token count.
- Folding the unpack into the GEMM's operand path is blocked on an FP8 UB→L1
  copy: `asc_copy_ub2l1` carries 16- and 32-bit element types only.
- The scale pass could move into the GEMM epilogue (L0C to UB, scale, store
  bf16), saving its read-back of the FP32 accumulator.
